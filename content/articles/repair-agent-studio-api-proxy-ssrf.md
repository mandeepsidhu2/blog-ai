Google’s July 20, 2026 Gemini Enterprise Agent Platform release notes disclose and fix server-side request forgery in the autogenerated `/api-proxy` backend for Agent Studio web applications created before July 1. The prescribed action is direct: regenerate the application and deploy the new version. The updated backend adds strict domain allowlisting for destination hostnames ending in permitted Google Cloud domains such as `*-aiplatform.clients6.google.com`.

Regeneration is necessary. It is not the entire verification plan. A proxy that accepts a destination from a browser sits at a parser, DNS, redirect, identity, and network boundary. Engineers need to prove which version is deployed, which destinations are accepted after canonical parsing, whether redirects are followed, where DNS resolves at connection time, what credentials the proxy carries, and what the runtime can reach if application validation fails.

## Decision Summary

Inventory every Agent Studio web application whose code was downloaded, generated, or deployed before July 1, 2026. Regenerate from Agent Studio, review the diff, deploy through a canary, and require a negative SSRF suite before moving traffic. Treat an unknown generation date as affected.

Do not patch the old handler with an improvised regular expression. Use the regenerated implementation as the vendor-supported baseline, then add defense in depth: a standards-compliant URL parser, exact scheme and port policy, no automatic redirects, destination revalidation on every hop, public-IP enforcement at connection time, least-privilege service identity, and outbound network controls.

The release note does not report a CVE, CVSS score, exploit prerequisites, affected package version, generated-code hash, or evidence that an already deployed application updates automatically. Those values are unknown. This article therefore makes no claim that a particular deployment was exploited or that every hostname-ending check is vulnerable. It defines the evidence needed to close the issue locally.

## What Changed and Who Is Affected

The [Gemini Enterprise Agent Platform release notes](https://docs.cloud.google.com/gemini-enterprise-agent-platform/release-notes) were last updated July 29, 2026. Their July 20 security entry says the affected surface is the autogenerated `/api-proxy` endpoint in web applications created before July 1, 2026 with Agent Studio. It instructs teams to regenerate and redeploy. The new code validates destination hostnames against allowed Google Cloud domain suffixes.

That wording creates four inventory states:

- generated before July 1 and deployed: affected until replaced and verified;
- generated before July 1 but never deployed: block deployment and regenerate;
- generated on or after July 1: verify the generated handler and test it anyway;
- generation date or lineage unknown: treat as affected because provenance cannot prove the fix.

The date applies to generated source, not merely the last deployment timestamp. A July 25 redeploy of code generated June 28 can still contain the old handler. Store the generator revision or a hash of the handler alongside the deployment artifact so future advisories can be answered mechanically.

The exact framework, HTTP client, DNS resolver, and deployment network are not reported in the release note. Verify the emitted source rather than assuming a language-specific control.

## Why a Hostname Suffix Needs a Label Boundary

“Ends with an allowed domain” is safe only if the comparison is defined precisely. If `allowed.example` is permitted, a raw string check such as `hostname.endsWith('allowed.example')` also accepts `notallowed.example`. The authorization rule needs an exact match or a preceding DNS-label boundary:

`host === suffix || host.endsWith('.' + suffix)`

For a wildcard pattern such as `*-aiplatform.clients6.google.com`, define whether the wildcard matches exactly one label, multiple labels, or an empty label. Normalize the hostname with the platform URL parser and IDNA processing before comparison. Reject user information, because RFC 3986 allows an authority such as `trusted.example@attacker.example`; the host is after the `@`, regardless of what a human notices first.

Do not validate the entire URL with one regular expression. The [OWASP Node.js SSRF guidance](https://owasp.org/www-community/pages/controls/SSRF_Prevention_in_Nodejs.html) warns that regex parsing, raw hostname checks, alternate IP formats, IPv6-mapped IPv4, Unicode, redirects, and DNS rebinding create bypasses. Even if your generated backend is not Node.js, those test categories remain useful.

This warning is not evidence that Google’s regenerated comparison is naive. The public note describes the intended hostname boundary, not the implementation details. Review and test the emitted handler before drawing a conclusion. The title’s “suffix trap” refers to a common local reimplementation error that teams can introduce while merging custom code, not a demonstrated bypass in the July fix.

Set input bounds before parsing: for example, reject a destination longer than 2,048 bytes, allow only `https:`, require port 443 or no explicit port, reject fragments and embedded credentials, and cap total request headers at the platform’s declared limit. These are operational guardrails, not universal URL standards; choose values that fit the generated application and API contract.

## Redirect and DNS Boundaries

A safe first URL can return a redirect to a forbidden destination. OWASP recommends disabling automatic redirects for allowlisted SSRF flows. If product behavior genuinely requires redirects, cap the chain—such as at three hops—and rerun scheme, hostname, port, DNS, and IP checks on every destination before sending credentials.

DNS introduces a time-of-check/time-of-use problem. A hostname can resolve to a public address during validation and a private address during connection. It can also return a mix of public and private A or AAAA records. Reject the whole resolution set when any address is loopback, private, link-local, multicast, unspecified, or otherwise special-purpose. Pin the validated address for the connection while preserving TLS server-name verification against the approved hostname.

Use the [IANA IPv4 special-purpose registry](https://www.iana.org/assignments/iana-ipv4-special-registry/iana-ipv4-special-registry.xhtml) and [IANA IPv6 special-purpose registry](https://www.iana.org/assignments/iana-ipv6-special-registry/iana-ipv6-special-registry.xhtml) rather than maintaining an incomplete list from memory. At minimum, the test suite should include `127.0.0.1`, `0.0.0.0`, `10.0.0.1`, `172.16.0.1`, `192.168.0.1`, `169.254.169.254`, `::1`, IPv4-mapped IPv6, and an arbitrary public host outside the allowlist.

## Identity and Network Containment

SSRF impact is determined by what the proxy can reach and what identity it carries. A browser user may be unable to call an internal service directly, while the backend can reach it with a service account or network path. [CWE-918](https://cwe.mitre.org/data/definitions/918.html) defines this confused-deputy pattern: attacker-controlled destinations cause the server to make unintended requests.

Give the proxy a dedicated identity with only the API permissions required by the generated app. Do not attach broad project administration, secret access, or deployment credentials. Avoid forwarding user-supplied authorization headers to arbitrary destinations. Construct outbound authentication after destination authorization, and scope tokens to the intended audience.

Constrain the HTTP contract as tightly as the destination. If the app needs only `POST` with JSON, reject `CONNECT`, `TRACE`, unexpected methods, streaming upgrades, user-controlled `Host`, proxy headers, and arbitrary content types. Cap request and response bytes, execution time, and concurrency. A destination allowlist does not prevent a caller from abusing an approved service through an overpowered method, header, or body.

Constrain egress so application validation is not the only wall. Deny loopback, link-local, private ranges, metadata endpoints, and general internet destinations unless the application explicitly needs them. Google’s guidance on [preventing lateral movement in Compute Engine](https://cloud.google.com/blog/products/identity-security/preventing-lateral-movement-in-google-compute-engine) recommends the v1 metadata API and VPC Service Controls as defense-in-depth measures against SSRF-driven credential access and exfiltration. The exact controls depend on whether the generated backend runs on Cloud Run, another managed runtime, or a custom environment.

Log decisions without leaking secrets. Record a request ID, canonical host, resolved address class, decision reason, redirect count, service revision, and latency. Do not log full query strings, tokens, or response bodies by default. Alert when the rejection rate exceeds a baseline—for example, 1% over 15 minutes—or when any metadata, private-address, or userinfo case is attempted.

## Test the Regenerated Handler

Build a sealed matrix before examining production traffic. Include positive cases for every necessary Google API hostname and negative cases for parser ambiguity, suffix confusion, DNS, redirects, methods, and body size.

Parser cases should cover uppercase hosts, a trailing dot, percent encoding, backslashes, multiple `@` characters, Unicode confusables, empty hosts, decimal or hexadecimal IP forms, IPv6 literals, and an explicit non-443 port. Domain cases should distinguish `allowed.example`, `sub.allowed.example`, `notallowed.example`, `allowed.example.attacker.test`, and an attacker-controlled subdomain that redirects.

Use an authorized test environment that cannot touch real internal services. The objective is to observe rejection before a network request, not to probe production infrastructure. For each case, assert the HTTP status, structured error code, zero upstream connection attempts, and absence of credentials in logs.

Run at least 65 negative cases: 25 parser cases, 20 hostname cases, 10 redirect chains, and 10 DNS/address cases. That count is an anti-omission checklist, not statistical proof. Add every discovered bypass as a permanent regression case.

## Engineering Decision and Migration Plan

First, create a deployment ledger. Record application owner, generated-source timestamp, repository revision, current deployment revision, runtime identity, ingress exposure, authorized upstreams, and rollback artifact. Require 100% inventory coverage before declaring remediation complete.

Second, regenerate in a clean branch and inspect the diff. Identify changes to URL parsing, hostname comparison, redirects, request headers, authentication, error handling, and dependencies. Do not overwrite local customizations blindly. Reapply only necessary changes after understanding whether they weaken the regenerated boundary.

Third, run static review and the negative suite. Confirm that the HTTP client uses zero automatic redirects, that DNS/address checks happen on the actual connection path, and that secrets are attached only after authorization. Verify outbound firewall or service-perimeter behavior independently from unit tests.

Fourth, canary at no more than 5% of traffic for at least one representative peak window. Compare success rate, p50/p95 latency, upstream error codes, rejected-destination counts, and credential/audience errors with the old version. The canary should use read-only or reversible workflows first.

Fifth, promote only when all security tests pass, legitimate upstream success is non-inferior within the declared margin, and rollback has been rehearsed. Retain the old image only for emergency recovery; do not route back to it if the incident condition can be triggered.

## Failure Modes and Comparability Limits

The first failure is assuming redeployment happened because a source generator was updated. Deployed artifacts are immutable until your pipeline replaces them. Verify the running revision from a response header, signed manifest, or platform metadata.

The second is overbroad wildcarding. A domain suffix controls naming, not ownership of every current and future subdomain. Keep the allowlist to the smallest documented service endpoints and review it quarterly. Remove retired hosts rather than accumulating permanent exceptions.

The third is breaking legitimate traffic and disabling the fix. That is why the migration needs a positive corpus and a canary. If a required API is missing, add its exact host with an owner and expiry; do not reopen arbitrary proxying.

The fourth is believing network controls alone are enough. Broad egress may return later, and internal services can still exist inside an allowed perimeter. Keep parser, authorization, DNS, redirect, identity, and network layers independent.

## Adoption Boundary: When Not to Use the Proxy

Do not use a general destination parameter when the application calls a fixed set of APIs. Map a short server-side operation identifier to a fixed base URL instead. This removes an entire class of attacker-controlled URL behavior and follows the [OWASP unvalidated redirect guidance](https://cheatsheetseries.owasp.org/cheatsheets/Unvalidated_Redirects_and_Forwards_Cheat_Sheet.html) preference for server-side identifiers.

Do not expose the proxy directly to unauthenticated internet traffic if its only caller is a managed frontend. Do not let it forward arbitrary methods, headers, bodies, or credentials. Do not preserve the old endpoint for compatibility after the new application is proven; compatibility is not worth retaining a known security boundary failure.

If you cannot identify the deployed source, restrict egress or disable `/api-proxy` until regeneration is complete. Availability loss is preferable to leaving a server-side deputy with unknown destination controls and privileged reachability.

## Production Readiness and Rollback

Define a release gate with zero accepted negative SSRF cases, zero unvalidated redirects, zero private or metadata connections, 100% deployment provenance, and 100% approved-host positive coverage. Require p95 latency within the application SLO and less than a 0.5 percentage-point legitimate-request regression during canary.

Rollback should mean switching to a known-safe previous product version or disabling the feature, not restoring the vulnerable handler. Keep a feature flag that removes proxy-backed actions while preserving static UI and human escalation. If a security assertion fails, stop the canary automatically and revoke the proxy identity’s tokens.

After promotion, sample rejection logs daily for seven days and weekly thereafter. Review new upstream requests as security changes. Re-run the suite whenever the generator, runtime, HTTP client, DNS layer, allowlist, or service identity changes.

Perform a retrospective incident check without claiming compromise. Search the affected deployment window for requests to unusual destinations, private or link-local addresses, metadata hostnames, repeated parser errors, unexplained response-size spikes, and service-account use outside the application’s normal APIs. Preserve relevant logs and rotate credentials if evidence indicates exposure. Absence of retained telemetry is an evidence gap, not proof that exploitation occurred or did not occur.
